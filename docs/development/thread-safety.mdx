---
title: Thread Safety
---

Some framework APIs are thread-unsafe. Calling them from a non-main-thread context (e.g. inside `Task.Run`, or after `await`-ing a database call) is not supported and can cause undefined behavior or crashes.

<Callout type="warning">
    If an API is marked thread-unsafe, don't call it directly from a background
    thread. Use its `Async` counterpart, or schedule the call back onto the main
    thread first.
</Callout>

## Core Rule

Thread-unsafe methods either carry <ApiRef name="ThreadUnsafeAttribute" /> (`[ThreadUnsafe]`) or say so in their XML comments - <ApiRef name="IEngineService" member="DispatchParticleEffect" /> is one of the latter - and must run on the game thread. Prefer their `Async` variant when one exists - it takes care of the dispatch for you; otherwise hand the call to `Core.Scheduler` yourself. Check `Core.IsGameThread` at runtime to branch explicitly:

```csharp
if (!Core.IsGameThread)
{
    Core.Scheduler.NextTick(() => player.SendChat("Hello!"));
}
else
{
    player.SendChat("Hello!");
}
```

## Dispatching to the Main Thread

The `*Async` counterparts listed further down already dispatch for you, so an `async` flow can call them directly. Everything else goes through <ApiRef name="ISchedulerService" /> (<ApiRef name="ISwiftlyCore" member="Scheduler" />), which has four ways to hand a call back to the game thread:

| Method                                                                    | Behavior                                                                |
| ------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| <ApiRef name="ISchedulerService" member="NextTick" />                     | Runs the callback on the next server tick                               |
| <ApiRef name="ISchedulerService" member="NextWorldUpdate" />              | Runs the callback on the next world update phase instead                |
| <ApiRef name="ISchedulerService" member="NextTickAsync" />                | Same as `NextTick`, but awaitable and able to return a value            |
| <ApiRef name="ISchedulerService" member="NextWorldUpdateAsync" />         | Same as `NextWorldUpdate`, but awaitable and able to return a value     |

The awaitable variants take either an `Action` (returning `Task`) or a `Func<T>` (returning `Task<T>`):

```csharp
int computedValue = await Core.Scheduler.NextTickAsync(() => 42);
```

<Callout type="warning">
    Don't pass an async callback (`Func<Task>`/`Func<Task<T>>`) to `NextTick`, `NextWorldUpdate` or their awaitable variants - those overloads are `[Obsolete]` and throw `InvalidOperationException`, since an async callback isn't guaranteed to resume on the game thread. Use the plain `Action`/`Func<T>` overloads instead.
</Callout>

The same service also has timer APIs (`Delay`, `Repeat`, `DelayAndRepeat`, `AddTimer`, ...) for work that is periodic rather than one-off - see [Scheduler](/docs/development/scheduler).

## Safe Usage Patterns

Prefer `Async` counterparts in any `async` flow (e.g. after a database call):

```csharp
public async Task NotifyPlayerAsync(IPlayer player)
{
    await player.SendChatAsync("Hello from an async flow.");

    using var sound = new SoundEvent("UI.CounterBeep", volume: 1.0f, pitch: 1.0f);
    sound.Recipients.AddAllPlayers();
    await sound.EmitAsync();
}
```

For anything else - a thread-unsafe API without an `Async` variant, or arbitrary code that has to run on the game thread - schedule it explicitly instead:

```csharp
await Core.Scheduler.NextTickAsync(() => player.SendChat("Executed on the main thread via the scheduler."));
```

    <ApiRef name="IEngineService" member="DispatchParticleEffect" /> is documented

    <ApiRef name="IEngineService" member="ExecuteCommand" /> has an
    `ExecuteCommandAsync` variant - use those from a background flow.
</Callout>

## Checklist

Find sync calls to thread-unsafe APIs running after an `await` (outside `Load`/event handlers), replace with the `Async` variant, or wrap with `Core.Scheduler.NextTick`/`NextWorldUpdate` (or their awaitable variants) if no `Async` variant exists. Don't fire-and-forget gameplay-critical calls - `await` them or handle failures explicitly.
